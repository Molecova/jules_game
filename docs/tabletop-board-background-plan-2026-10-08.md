## 목표와 범위

실제 목재 프레임과 도색한 모형 지형으로 만든 보드게임이 휴대폰 화면 안에 있는 느낌을 만든다. 인공적인 발광보다 재질·두께·모서리·그림자로 입체감을 표현한다. **게임판과 배경만 구현한다.** 유닛은 현재의 간결한 딱지를 유지한다.

게임판의 5×6 전투 칸, 배치·이동·사거리·공격·스킬·적 편성·경제·밸런스·저장 규칙은 유지한다. 유닛 미니어처, 새로운 칩·무기 디자인, 스킬 이펙트 개편, 상점·지도·이벤트 UI 개편은 작업 범위에 포함하지 않는다. 테두리의 돌·풀·폐허는 장식이며 전투 장애물이 아니다.

5시간은 **1막을 기준 품질로 완성하는 기본안**, 10시간은 그 결과에 **다른 막의 모델·배경과 최적화를 더하는 확장안**이다. 아래 시간은 순차 작업 예상이며 실제 실행을 예약하거나 이미 수행했다는 뜻은 아니다. 저장소 접근 대기나 외부 에셋 다운로드 지연은 예상 작업 시간에 포함하지 않는다.

## 0. 포크·독립 저장소 준비

원본은 `Molecova/jules_game`, 작업 브랜치는 `ccr-5e12923f-aw0cjb`다. 기준 커밋의 전체 변경 이력을 유지한 독립 복제본이 `/workspace/jules_game-tabletop3d`에 있고, 3D 시제품은 원본의 별도 `tabletop-a-3d` 브랜치에 게시되어 있다. 로컬 브랜치는 `main`, 기존 원격 이름은 `upstream`이다.

현재 로그인 계정은 원본 소유자 `Molecova`다. GitHub에서는 자기 저장소를 같은 계정에 공식 포크할 수 없으므로, 이 계정에서는 **이력을 보존한 새 저장소**로 분리한다. 다른 계정 소유의 공식 포크를 원하는 경우 그 저장소 URL을 사용한다.

목표 원격은 `Molecova/jules_game-tabletop3d`다. 이전 생성 요청은 앱 권한 부족으로 거절됐다(403). 이번 재확인에서도 API와 Git으로 접근할 수 없었다(404 / Repository not found). 없는 저장소와 앱에 허용되지 않은 저장소를 이 응답만으로 구분하지 않는다. 원격 분리가 완료됐다고 표시하지 않는다.

빈 목표 저장소 생성과 앱 접근 허용이 준비되면 아래를 수행한다.

1. 목표 저장소가 맞는지, 비어 있는지, 실제 읽기·쓰기 접근이 가능한지 확인한다. 기존 내용이 있으면 덮어쓰거나 강제 푸시하지 않고 먼저 비교한다.
2. 기존 `upstream`을 유지하고 새 저장소를 `origin`으로 연결한다. 현재 `main`의 전체 이력을 푸시하고 기본 브랜치로 설정한다.
3. 원본과 독립 저장소의 커밋·브랜치를 확인하고 독립 저장소 URL, 플레이 링크, 개발 환경 안내를 갱신한다.
4. 이후 보드·배경 변경은 독립 저장소에만 푸시한다. 준비 전에는 현재 3D 브랜치에 계획·미리보기만 게시하고 원본 작업 브랜치는 유지한다.

앱 접근이 확인된 빈 저장소에 연결할 때 사용할 명령은 다음과 같다. **아직 실행 완료한 명령이 아니다.**

```bash
cd /workspace/jules_game-tabletop3d
git remote add origin https://github.com/Molecova/jules_game-tabletop3d.git
git push -u origin main
```

## 5. 파일과 구현 방법

- `v4/tabletop4.js`: 게임 상태를 읽는 기존 연결을 유지한다. 환경 생성·재질·조명 코드가 복잡해질 때만 `tabletop-environment4.js`와 `tabletop-materials4.js`로 분리한다. 분리 자체에 앞 시간을 쓰지 않는다.
- `v4/assets/tabletop/`: 실제 사용한 목재·석판 등 재질 파일. 최초 재질은 최대 1K 해상도로 시작한다. `ATTRIBUTION.md`에 출처·라이선스·축소/변환 여부를 기록한다.
- `v4/tabletop4.css`: 보드 주변 바탕과 보드 캔버스 크기에 필요한 변경만 한다. HUD·상점·지도 디자인은 이번 작업에서 유지한다.
- `v4/game4.js`: 카메라와 보드 연결에 꼭 필요한 화면 좌표 처리만 변경 가능하다. 경제·진행·전투 규칙을 조정하지 않는다.
- `tests/browser-tabletop4.cjs`: 새로운 구도에서도 30개 칸 입력, 드래그, RNG 분리, 전투 동치, 복귀를 검사한다.
- `docs/tabletop-evidence/`: 같은 편성·같은 화면 크기로 찍은 전후 화면과 검사 기록. 막별 디자인 미리보기와 실제 원정 기록을 구분한다.

지형과 질감의 변화는 원정 RNG를 사용하지 않는다. 같은 막의 시각 구성은 전용 시각 시드로 재현한다. 보드 교체 시 GPU 자원을 해제하고, 반복되는 돌·풀과 타일은 가능한 한 지오메트리·재질을 공유한다.

## 6. 완료 검사와 품질 기준

1. **게임 화면으로 확인:** 390×844·360×640에서 준비와 전투를 각각 확인한다. 768×1024도 유지한다. 큰 홍보 이미지보다 이 화면에서 재질·두께·지형이 보이는 것을 우선한다.
2. **실제감:** 깎인 프레임 모서리, 목재 결, 판의 적층 단면, 딱지·지형의 접촉 그림자가 확인된다. 넓은 무늬 반복·과도한 광택·모서리 깜빡임이 없다.
3. **읽기 쉬움:** 30개 칸이 연속적으로 구분된다. 모든 딱지와 체력·예고 표시가 읽히고 배경이 주요 버튼을 가리지 않는다. 지형에 의한 오클릭이 없다.
4. **규칙 보존:** 엔진·능력치·적 편성·저장 모듈의 변경이 없는지 확인한다. 기존 회귀 검사와 동일 편성 전투 비교를 통과한다. 렌더링 때문에 원정 RNG가 변하지 않는다.
5. **입력·복귀:** 각 화면 크기의 30개 칸 화면 좌표 왕복 검사, 보드↔창고 드래그, 명시적 2D 모드와 WebGL 컨텍스트 손실 복귀가 통과한다.
6. **자원:** 1→5막 전환을 20회 반복해 자원 수가 첫 순환 이후 계속 증가하지 않는지 확인한다. 폴리곤·드로콜·텍스처 사용량은 실제 측정값을 기록한다.
7. **성능 목표:** 초기 목표는 장면 최대 10만 삼각형·150드로콜·텍스처 GPU 메모리 약 32MiB 이하다. 모바일 낮은 품질은 30fps를 목표로 하고 보드 장식·그림자부터 줄인다. 숫자는 예산이며 충족 여부를 측정해 보고한다. 클라우드 소프트웨어 GPU의 프레임을 실제 휴대폰 성능으로 해석하지 않는다.
8. **배포:** 브라우저 예외·콘솔 오류 0, 전후 화면과 검사 기록 저장, 실제 접근되는 플레이 링크 확인. 독립 원격이 막혀 있으면 그 사실과 미리보기 브랜치를 명시한다.

실제 기기 접근이 없다면 휴대폰에서의 프레임·발열·배터리는 미검증으로 남긴다. 추가 모델링 때문에 보드 배치나 원정 규칙을 변경해서 성능을 맞추지 않는다.
